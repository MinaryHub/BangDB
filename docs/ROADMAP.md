# 실서비스 DB로 쓰기 위한 보완 검토와 개발 계획

> 이 문서가 BangDB의 **기준 개발 계획**입니다. [시계열·인메모리 검토](REVIEW-timeseries-inmemory.md)의 단계 계획은 여기 통합되었습니다.

## 0. 진행 현황 — 1단계(운영 안정화) 완료

| ID | 항목 | 상태 | 결과·근거 |
|----|------|------|-----------|
| P0-1 | 스냅샷 읽기 (읽기가 커밋을 막지 않음) | ✅ | Pager를 WAL 모드 방식(페이지 버전 + 스냅샷 + 리더를 고려한 체크포인트)으로 재작성. 커밋 fsync 2회 → 1회 |
| P0-2 | 쿼리 취소·타임아웃 | ✅ | `ExecContext/QueryContext/BeginContext`, `Options.QueryTimeout`, 256행마다 확인, 중단 시 문장 롤백 |
| P0-3 | 스트리밍 결과 커서 | ✅ (일부) | 정렬·집계 없는 SELECT 스트리밍, `ORDER BY … LIMIT`은 top-K만 유지. **외부 정렬은 2단계로 이동(P1-14)** |
| P0-4 | 디렉터리 fsync | ✅ | 파일 생성·백업·스냅샷 설치 후 |
| P0-5 | 페이지 체크섬 + 무결성 검사 | ✅ | 페이지별 CRC32(포맷 v3), `IntegrityCheck`/`.check`: 트리 구조·페이지 누수/중복·인덱스 일치 |
| P0-6 | AUTOINCREMENT 보장 | ✅ | 시스템 시퀀스 트리에 최대 id 기록 |
| P0-7 | 장애 내성 테스트 | ✅ | 퍼저 5종(각 45~60초), `kill -9` 1,000회 |
| P0-8 | 파일 포맷 버전 정책 | ✅ | 헤더 포맷 버전 3, 다른 버전은 설명과 함께 거부 |
| P1-13 | 드라이버 context | ✅ (일부) | context 전달·스트리밍 완료. `ColumnTypes`·이름 있는 파라미터는 2단계 |

### 재측정 (같은 시나리오, 1단계 전 → 후)

| # | 시나리오 | 전 | 후 |
|---|----------|----|----|
| M2 | 긴 조회 실행 중 커밋 대기 | **1분 50초** | 최대 21.7 ms (5초 동안 커밋 5,732건) |
| M1 | 인덱스 없는 조인 (1,500 × 200,000) | 1분 50초, 중단 불가 | 같은 비용이지만 타임아웃으로 중단 가능 (해시 조인은 P1-5) |
| M3 | `SELECT *` 200,000행 | 121 MB 할당 | 힙 증가 4 MB (스트리밍) |
| M4 | `ORDER BY … LIMIT 10` (200,000행) | 289 ms | 157~173 ms, 메모리는 top-K만 (인덱스 순서 활용은 P1-5) |
| M5 | `k = 5 OR k = 7` | 91 ms | 74 ms (OR 인덱스 활용은 P1-5) |
| M6 | 8 고루틴 자동 커밋 | 1,277 커밋/초 | 1,546 커밋/초 (그룹 커밋은 P1-6) |
| M8 | AUTOINCREMENT 최대 id 삭제 후 | id 재사용 | 재사용 안 함 |
| C1~C3 | 디렉터리 fsync, 드라이버 context, 페이지 체크섬 | 없음 | 적용 |

### 새 테스트가 찾아내 고친 결함
1. **체크포인트/복구 중단 시 DB 손상** (`kill -9` 토처 테스트가 4회차에 발견): 체크포인트와 복구가 헤더(0번 페이지)를 다른 페이지보다 먼저 써서, 그 사이에 죽으면 파일이 실제보다 새로운 커밋을 가리키고 복구가 필요한 WAL 커밋을 건너뛰었습니다. 헤더를 마지막에 쓰도록 수정했고, failpoint 재현 테스트를 추가했습니다. 수정 후 1,000회 모두 통과(응답한 커밋 손실 0, 진행 중 커밋은 전부 반영 353회·미반영 647회, 무결성 문제 0).
2. **B+트리 페이지 디코더 패닉** (퍼저 발견): 손상된 페이지에서 범위 밖 접근. 모든 필드 경계 검사 추가.
3. **행 디코더 메모리 폭주** (퍼저 발견): 손상된 값 개수만큼 미리 할당. 입력 길이로 상한 검사.

### 1단계에서 남긴 것 (2단계로 이동)
- **P1-14 (신규) 외부 정렬·대용량 그룹핑**: LIMIT 없는 `ORDER BY`, `GROUP BY`, `DISTINCT`는 여전히 메모리에서 처리.
- 드라이버 `ColumnTypes`, 이름 있는 파라미터 (P1-13 나머지).
- 열린 스냅샷이 오래 유지되면 WAL과 메모리 내 페이지 버전(최대 64 MiB, 초과분은 WAL에서 다시 읽음)이 커지는 구조적 특성 → 관측 지표(P2-1)로 노출 예정.

## 1. 결론 요약 (1단계 착수 전 평가)

현재 BangDB는 "**짧은 쿼리 위주의 단일 프로세스 임베디드 DB**"로는 쓸 수 있지만, 실서비스 DB로 쓰기 전에 반드시 고쳐야 할 문제가 있습니다.

| 영역 | 현재 수준 | 판단 |
|------|-----------|------|
| 데이터 안전성 (원자성·크래시 복구) | WAL·복구·문장 원자성 테스트 통과 | 양호. 단, 디렉터리 fsync 누락, 페이지 체크섬 없음 |
| 동시성 | 단일 writer + 리더 | **❌ 긴 읽기 쿼리가 모든 커밋을 막음 (실측 1분 50초)** |
| 자원 통제 | 쿼리 취소·타임아웃 없음, 결과 전체 메모리 적재 | **❌ 하나의 무거운 쿼리가 서비스 전체를 멈출 수 있음** |
| SQL 기능 | 기본 CRUD·JOIN·집계 | ⚠️ 서브쿼리, UPSERT, 복합 인덱스 등 앱 개발에 자주 쓰는 기능 부족 |
| 쿼리 성능 | 인덱스 동등/범위 검색은 양호 | ⚠️ OR, ORDER BY+LIMIT, 인덱스 없는 조인이 매우 느림 |
| 쓰기 처리량 | 트랜잭션 내 ~27µs/행 | ⚠️ 자동 커밋 ~1,300 커밋/초에서 포화 (그룹 커밋 없음) |
| 운영 | 온라인 백업·복제·CLI | ⚠️ 무결성 검사, 메트릭, 덤프/복원, VACUUM 없음 |

**권장:** 시계열·인메모리 확장보다 **1단계(운영 안정화, P0)를 먼저** 끝내야 합니다. 특히 P0-1(읽기가 커밋을 막는 문제)은 Pager 구조를 바꾸는 작업이라 이후 모든 확장의 기반이 됩니다.

|---|----------|------|------|
| M1 | 인덱스 없는 컬럼으로 조인 (1,500 × 200,000행) | **1분 50초** | nested-loop 조인만 존재 |
| M2 | M1 실행 중 단일 행 INSERT 커밋 | **1분 50초 대기** | 리더가 문장 실행 내내 `commitMu` 읽기 락을 보유, 커밋은 쓰기 락 필요 |

| M8 | `AUTOINCREMENT` 최대 id(3) 삭제 후 INSERT | id 3 재사용 | 최대 rowid를 별도 저장하지 않음 |
| M9 | 600바이트 TEXT 인덱싱 | 에러 (최대 496바이트) | 인덱스 키 길이 제한 |
| M10 | `name = 'kim'` vs 저장값 `'Kim'` | 불일치 | 대소문자 무시 비교(COLLATE NOCASE) 없음 |
| M11 | 서브쿼리 `IN (SELECT ...)`, `ON CONFLICT` | 구문 에러 | 미구현 |
| C1 | 코드 검토: 파일 생성·`rename` 후 디렉터리 fsync | 없음 | 전원 장애 시 새 DB 파일/백업 파일/스냅샷 교체가 사라질 수 있음 |
| C2 | 코드 검토: `database/sql` 드라이버의 `context` | 무시됨 | 취소·타임아웃이 전달되지 않음 |
| C3 | 코드 검토: DB 파일 페이지 체크섬 | 없음 (WAL·복제 전송에만 CRC) | 디스크 비트 오류를 감지하지 못하고 잘못된 결과를 반환할 수 있음 |

## 3. 보완 항목

규모: S = 1~3일, M = 1~2주, L = 3주 이상 (1인 기준 추정)

### P0 — 실서비스 투입 전 필수

| ID | 항목 | 근거 | 방안 | 규모 | 완료 기준 |
|----|------|------|------|------|-----------|
| P0-1 | **읽기가 커밋을 막지 않게 (스냅샷 읽기)** | M2 | SQLite WAL 모드 방식: 커밋은 WAL에 **추가(append)만** 하고 DB 파일에는 즉시 쓰지 않음. 리더는 시작 시점의 WAL 위치까지만 보는 스냅샷으로 읽음. 체크포인트(WAL → DB 파일)는 백그라운드에서, 그 페이지를 볼 수 있는 리더가 없을 때 수행. 부수 효과로 커밋당 fsync가 1회로 줄어듦 | L | M1 실행 중 커밋 대기 < 10ms. 기존 크래시 테스트 + 체크포인트 도중 크래시 테스트 통과 |
| P0-2 | **쿼리 취소·타임아웃** | M1, C2 | `ExecContext/QueryContext` 추가, 스캔·조인 루프에서 주기적으로 `ctx.Err()` 확인. `Options.QueryTimeout`, 드라이버에 context 전달 | S | 타임아웃 시 즉시 `context.DeadlineExceeded` 반환, 락 해제 확인 테스트 |
| P0-3 | **스트리밍 결과 커서** | M3 | 정렬·집계·DISTINCT가 없는 쿼리는 `Rows.Next()`마다 한 행씩 생성 (P0-1의 스냅샷이 있어야 리더가 오래 열려 있어도 안전). 정렬이 필요하면 메모리 한도 초과 시 임시 파일 외부 정렬 | M | 100만 행 `SELECT *` 순회 시 메모리 사용량이 행 수와 무관하게 일정 |
| P0-4 | **디렉터리 fsync** | C1 | 새 DB 파일 생성, 백업 `rename`, 스냅샷 설치 후 상위 디렉터리 `Sync()` | S | 코드 리뷰 + 해당 경로 단위 테스트 |
| P0-5 | **페이지 체크섬 + 무결성 검사** | C3 | 페이지마다 CRC32(또는 xxhash) 보관(페이지 끝 4바이트 예약). `PRAGMA integrity_check` 상당 기능: B+트리 구조, 키 순서, 인덱스↔테이블 일치, free list 검사. CLI `.check` | M | 페이지 1바이트 변조 시 읽기 에러로 감지, 무결성 검사기가 손상 위치 보고 |
| P0-6 | **AUTOINCREMENT 보장** | M8 | 테이블 카탈로그에 최대 발급 rowid 저장, AUTOINCREMENT 테이블은 재사용 금지 | S | 최대 id 삭제 후 재삽입 시 새 id |
| P0-7 | **장애 내성 테스트 확대** | — | `go test -fuzz`: SQL 파서, 행/키 디코더, B+트리 페이지 디코더. 프로세스 `kill -9` 반복 토처 테스트(쓰기 중 강제 종료 → 재시작 → 무결성 검사). 장시간 소크 테스트 | M | 퍼저 각 1시간 무결함, 토처 1,000회 무결함 |
| P0-8 | **파일 포맷 버전 정책** | — | 헤더에 포맷 버전 필드 명시, 상위 버전 파일은 열기 거부, 하위 버전은 자동 업그레이드 경로 정의 | S | 버전 불일치 테스트 |

### P2 — 운영·확장

| ID | 항목 | 방안 | 규모 |

### 순서에 대한 근거
- **P0-1을 가장 먼저**: Pager의 커밋/체크포인트 구조를 바꾸므로, 그 위에 올라갈 스트리밍 커서(P0-3), 그룹 커밋(P1-6), 체크섬(P0-5), 시계열 chunk가 모두 영향을 받습니다. 나중에 바꿀수록 비용이 커집니다.
- 복제는 Frame(페이지 이미지) 기반이므로 P0-1 이후에도 프로토콜 변경 없이 유지됩니다. 단, Frame 생성 시점이 "WAL append"로 바뀌는 것만 조정하면 됩니다.
- 복합 인덱스(P1-1)는 시계열(5단계)의 선행 조건이므로 2단계에 둡니다.

## 5. 현재(1단계 완료 시점) 사용 가이드

- **적합:** 단일 프로세스 앱의 업무 데이터 저장, 수 GB 이하, OLTP 중심. 긴 조회가 섞여도 쓰기는 막히지 않습니다.
- **조회에는 타임아웃을:** `QueryContext`나 `Options.QueryTimeout`으로 상한을 두세요. 인덱스 없는 조인은 여전히 느립니다 (`EXPLAIN`의 `SCAN` 확인).
- **`Rows`는 끝까지 읽거나 `Close`:** 열린 커서는 스냅샷을 붙잡아 체크포인트를 미룹니다.
- **큰 정렬·집계 결과는 LIMIT으로:** LIMIT 없는 `ORDER BY`/`GROUP BY`/`DISTINCT`는 메모리에서 처리됩니다.
- **대량 쓰기는 트랜잭션으로 묶기:** 자동 커밋은 ~1,500건/초 수준입니다 (그룹 커밋은 2단계).
- **정기 점검·백업:** `db.Backup()`을 주기적으로, `db.IntegrityCheck()`를 배포 전·장애 후에 실행하세요.
