# 실서비스 DB로 쓰기 위한 보완 검토와 개발 계획

> 이 문서가 BangDB의 **기준 개발 계획**입니다. [시계열·인메모리 검토](REVIEW-timeseries-inmemory.md)의 단계 계획은 여기 통합되었습니다.

## 8. SQL 완성도와 셸 (완료)

7단계 이후 "현재 제약 사항"에 남아 있던 SQL 공백과 CLI 사용성을 보완했습니다.

| 항목 | 결과 |
|---|---|
| CTE | `WITH`·`WITH RECURSIVE`(SELECT/INSERT/UPDATE/DELETE, 서브쿼리·뷰). CTE는 문장당 한 번, 처음 참조될 때 계산해 파생 테이블처럼 훑음. 재귀는 재귀 SELECT의 플랜을 한 번 만들고 작업 테이블만 바꿔 반복 실행(`internal/engine/cte.go`) |
| 식 인덱스 | 키 부분이 식인 인덱스. 식은 카탈로그에 테이블의 컬럼 이름으로 정규화한 SQL 텍스트로 저장하고, 질의 조건의 한쪽을 같은 방식으로 정규화해 일치하면 사용. 타입 추론이 되는 식은 컬럼과 같은 키, 그 밖에는 숫자를 정규화한 키(동등·IN 전용) (`internal/engine/keyexpr.go`) |
| 생성 컬럼 | 쓰기 시 계산·저장(`prepareRow`), 일반 컬럼처럼 인덱스·제약 적용 |
| 테이블 값 함수 | `json_each`·`json_tree`·`generate_series`. 조인의 한 단계로, 앞 단계 행마다 인수를 평가해 행을 스트리밍(`internal/engine/tablefunc.go`) |
| CLI 셸 | 표준 라이브러리만으로 raw 모드 줄 편집기(히스토리·자동 완성), 출력 형식, 원격 `.tables`/`.schema` |
| 검증 | 기능별 테스트(`cte_test.go`, `exprindex_test.go`, `tablefunc_test.go`, `cmd/bangdb/shell_test.go`), 덤프·재오픈 왕복, 퍼저 시드 추가, 메모리 저장 방식으로도 실행 |

- **남긴 것:** CTE·뷰의 조건 push-down(지금은 전체를 계산), 상호 재귀, 식 인덱스의 covering 사용과 `ON CONFLICT (식)`, 계산만 하는 `VIRTUAL` 생성 컬럼, 테이블 값 함수가 있는 조인의 재배치, 이름 있는 윈도.

- 남은 비례 메모리: 페이지별 WAL 버전 항목, VACUUM 빌더의 잎 목록(페이지당 수십 바이트) — 1억 행 수준에서 다시 측정 필요.

## 0. 진행 현황 — 6단계(운영·분산) 및 이월 항목 완료

계획한 단계(0~6)와 앞 단계에서 미뤄 둔 항목을 모두 구현했습니다. 남은 것은 아래 "남긴 것"의 개선 과제입니다.

| 항목 | 결과 |
|------|------|
| P2-6 SQL | 윈도우 함수(`ROW_NUMBER/RANK/DENSE_RANK/PERCENT_RANK/CUME_DIST/NTILE/LAG/LEAD/FIRST_VALUE/LAST_VALUE/NTH_VALUE`, 집계 + `ROWS/RANGE` 프레임, 그룹 질의 위에서도), JSON 함수(`json_extract/set/insert/replace/remove/patch/type/array/object/group_array/group_object` 등)와 `->`/`->>` |
| P2-1 관측성 | `db.Stats()`(문장·오류·슬로우, 커밋 수·시간, 락 대기, WAL·체크포인트, 페이지/노드 캐시 적중, 스냅샷 지연, 커서), `Options.SlowQueryThreshold/OnSlowQuery`, `EXPLAIN ANALYZE`, CLI `.stats` — 오버헤드는 측정 오차 수준 |
| P2-2 덤프·이관 | `Dump`(스냅샷에서 SQL), `ImportSQL`(Dump·SQLite `.dump` 호환: PRAGMA/트랜잭션 무시, 부모보다 먼저 만든 자식 테이블 대기, `sqlite_sequence`, 마지막에 FK 일괄 검사, 전부 아니면 전무), CSV 가져오기·내보내기, CLI `.dump/.read/.import/.export` — 10만 행 덤프 0.1 s, 가져오기 1.1 s |
| P2-5 암호화 | AES-256-XTS 페이지 암호화(파일·WAL, 헤더 제외), 키 확인 값으로 잘못된 키 보고, 백업·VACUUM·복제본 각자 키, `BackupWithKey`로 키 교체 — IEEE 1619 벡터·크래시 토처 통과 |
| P2-3 복제 | 프로토콜 v2: replica ack → replica별 지연(커밋 수·시간), **반동기**(`SyncReplicas`, 타임아웃 시 비동기로 강등), **term 펜싱**(승격 시 term+1, 새 term 노드가 닿으면 옛 primary는 읽기 전용), **PITR**(`Archiver`: 베이스 백업 + 커밋 세그먼트(선택 AES-GCM), `Restore`로 커밋 번호·시각까지) |
| P2-4 서버 모드 | `server`(TCP/TLS, 비밀번호·콜백 인증, 연결 제한·유휴 종료, 세션 = 트랜잭션, 스트리밍·취소), `client`, `database/sql` DSN `bangdb://user:pw@host:port`, CLI `-listen`/`-connect` — 루프백 단건 왕복 44 µs |
| 플래너 (P1-5 ④⑤) | `ANALYZE` 통계 + 비용 기반 조인 순서(쓴 순서보다 2배 이상 쌀 때만), 통계로 인덱스 선택, **covering index**(5만 행 범위 집계 139 → 11 ms) |
| 기타 이월 | `DB.Prepare`(파싱 1회·문장 전용 플랜), 시계열 블록 compaction, 메모리 테이블 `persist` 스냅샷 |

- **남긴 것:** 단건 조회는 여전히 약 2 µs(실행 상태·행 디코드 할당과 GC가 주 비용). 시계열의 열 단위 집계·블록 요약·태그 인덱스. 자동 장애 조치(합의 기반 리더 선출). 이름 있는 윈도(`WINDOW w AS`). 통계는 평균값이라 치우친 분포는 잘못 추정할 수 있음. (트리거는 7단계, 식 인덱스·테이블 값 함수는 8단계에서 추가)

## 0-5. 5단계(시계열 테이블) 완료 기록

| 항목 | 결과 |
|------|------|
| 테이블 | `CREATE TABLE cpu (ts INTEGER NOT NULL, host TEXT, usage REAL) USING timeseries WITH (time_column = ts, time_unit = 's', retention = '30 days', block_rows = 1024)` — 시간 컬럼은 정수 epoch(s/ms/us) |
| 시간 = 위치 | rowid = `시각 << k | 순번`이라 rowid 순서가 시간 순서. 시간 조건은 rowid 범위 스캔(`SEARCH … USING TIME RANGE`), `ORDER BY ts [DESC] LIMIT n`은 정렬 없이 처리 |
| 저장(chunk) | 최근 행은 개별 항목, `block_rows`개가 쌓이면 **열 지향 압축 블록**으로 봉인: 시각·rowid는 delta-of-delta, 정수는 delta-of-delta/zigzag 중 작은 쪽, 실수는 Gorilla XOR, 문자열은 사전, 그 외는 행 레코드. 봉인된 행의 수정·삭제는 덮어쓰기 항목(삭제 표시)으로 처리해 블록을 다시 쓰지 않음. 모두 B+트리 하나 안에 있어 WAL·백업·복제·VACUUM·무결성 검사가 그대로 적용 |
| 보존 정책 | `retention`: 블록 봉인 시 (가장 최근 행의 시각 − 보존 기간)보다 오래된 블록을 통째로 제거 (블록 단위, 데이터 시각 기준) |
| 삭제 | 시간 조건만 있는 `DELETE`는 블록 단위 범위 삭제(일반 경로 대비 5~16배) |
| 함수 | `time_bucket(width, ts [, unit])` — 정수 epoch 또는 날짜 텍스트, width는 숫자 또는 `'5 minutes'` |
| 제약 | 보조 인덱스·PK·UNIQUE 없음(시간 순서가 기본 접근 경로), 시간 컬럼은 INTEGER |
| 공통 개선 | **지연 페이지 인코딩**(Pager): 쓰기 뷰는 수정한 B+트리 노드를 디코드된 상태로 들고 있다가 커밋 또는 바이트가 필요할 때 한 번 인코딩, 세이브포인트에는 노드 복사본 보관 → 모든 테이블의 쓰기 경로 개선 |
| 검증 | 압축 코덱 왕복·퍼징, 저장소 모델 테스트(순서·역순·동일 시각 삽입, 봉인 행 수정·삭제, 범위 삭제, 1만 행·697블록), 공통 적합성 테스트, **SQL 결과를 같은 데이터의 일반 테이블과 비교**(무작위 범위·정렬·집계·조인·시각 변경·삭제), 보존·롤백·스냅샷·VACUUM·재오픈, 크래시 토처·경합 검사·퍼저 |

### 1천만 포인트 벤치마크 (`go run ./internal/tsbench`, 파일 DB, 4코어)

호스트 1,000개 × 10초 간격 10,000시점. 비교용 일반 테이블(시간 인덱스 포함)은 200만 포인트.

| 항목 | 시계열 (1천만) | 일반 테이블 (200만) |
|------|------|------|
| 수집 (500행 INSERT, 20만 행마다 커밋) | **25.5만 포인트/초** (39초) | 29.8만 포인트/초 |
| 파일 크기 | **24.0 바이트/포인트** (240 MB) | 133 바이트/포인트 (266 MB) → **5.5배 작음** |
| 최근 5분, 전체 호스트 평균 | 10.7 ms | 25.4 ms |
| 최근 1시간, 한 호스트, 5분 버킷 | 181 ms | 274 ms |
| 최근 1시간, 호스트별 평균 | 197 ms | 346 ms |
| 최신 10개 (`ORDER BY ts DESC LIMIT 10`) | 0.24 ms | 0.10 ms |
| 전체 구간 1시간 버킷 집계 | 5.6 s (행당 0.56 µs) | 1.0 s / 200만 (행당 0.50 µs) |
| 가장 오래된 1시간 삭제 (36만 행) | **0.28 s** | 1.4 s |

- 같은 단계에서 수집 경로를 개선했습니다: 처음 구현은 5.1만 포인트/초였고, 방금 쓴 페이지의 재디코드 제거(점 조회가 뷰의 노드 사용) → 메타 키를 최근 행과 같은 리프에 배치 → 지연 페이지 인코딩으로 25.5만이 되었습니다(한 행짜리 INSERT 기준 21.1 → 7.8 µs/행).
- **남긴 것:** 호스트 같은 태그 조건은 시간 범위 안을 훑으며 거릅니다(태그 인덱스 없음). 전체 구간 집계는 블록 디코드 + 행 단위 실행기라 행당 약 0.5 µs — 열 단위(벡터화) 집계와 블록별 요약(min/max/count) 활용은 이후 과제. 덮어쓰기 항목이 많이 쌓인 블록의 재압축(compaction)은 6단계에서 추가: 블록 범위 안의 변경 항목이 block_rows/4개가 되면 블록을 변경 반영해 다시 인코딩하고(늦게 들어온 행이 많으면 block_rows 단위로 분할), 열 단위 집계·블록 요약·태그 인덱스는 여전히 이후 과제입니다.

## 0-4. 4단계(인메모리 최적화) 완료 기록

| 항목 | 결과 |
|------|------|
| 메모리 저장 방식 | `CREATE TABLE … USING memory`: 행과 인덱스를 페이지가 아닌 **영속(persistent) B+트리**(`internal/memtree`, 경로 복사)에 보관. 페이지 인코드·디코드와 WAL 기록이 없음. 행은 포인터 없는 행 레코드(`[]byte`)로 보관해 메모리 사용량과 GC 부담을 줄임 |
| 트랜잭션 연동 | Pager **객체 슬롯**(`View.Obj/SetObj`): 페이지와 같은 규칙으로 커밋 시 공개, 스냅샷은 커밋 시점의 트리를 그대로 봄, 세이브포인트는 루트만 되돌림. 같은 트랜잭션 안에서는 변경 토큰으로 노드를 제자리 수정(세이브포인트마다 새 토큰 → 되돌아갈 상태는 불변) |
| 의미 | MySQL MEMORY 엔진과 같음: 스키마는 파일에 남고 데이터는 프로세스 메모리에만 존재(재시작 시 빈 테이블). 백업·복제 대상 아님. 내구성 테이블이 메모리 테이블을 FK로 참조하는 것은 금지. **6단계**: `WITH (persist = true)`면 정상 종료 시 스냅샷 파일로 저장해 다음 열기에서 복원(커밋 순번은 그대로라 복제와 충돌 없음) |
| 공통 개선 (모든 저장 방식) | 커밋한 페이지의 디코드된 노드를 공유 캐시로 넘김, 삽입 경로의 내부 노드는 읽기용 노드로 내려가고 분할 때만 복사, 스트리밍 질의 전용 실행 경로, 동기 실행 시 취소 컨텍스트 생략, 질의당 할당 51 → 28개 |

### 2단계 테스트가 찾아내 고친 결함
1. `SELECT * … ORDER BY 2` 패닉 (퍼저 발견): ORDER BY 순번을 `*` 확장 전 목록으로 해석. 확장된 출력식 기준으로 수정.
2. 긴 공통 접두사(495바이트 초과)를 공유하는 키 수만 개에서 동등 조회가 그룹 전체를 훑어 44 ms (측정 중 발견). 잘린 키 뒤에 전체 키 해시를 붙여 18 µs로 개선.
3. 자식 행의 `SET NULL` 처리 중 이미 삭제된 부모를 다시 검사해 FK 오류: 변경된 FK 컬럼만 재검사하도록 수정.
4. 벤치마크가 스트리밍 `Rows`를 닫지 않아 고루틴·스냅샷이 쌓이던 문제 수정 (측정값 왜곡 원인).
5. **그룹 커밋의 카탈로그 공개 경쟁** (`-race`가 간헐적으로 발견): 커밋이 대기열에 들어간 뒤에 카탈로그를 붙여, 다른 writer의 fsync가 먼저 공개하면 DDL 직후 커밋이 이전 카탈로그와 함께 보일 수 있었음. 카탈로그를 `PrepareCommit` 인자로 넘겨 대기열 등록 전에 설정하도록 수정.

### 2단계에서 남긴 것
- **P1-5 ④ ✅**: `ANALYZE`가 인덱스별 키 접두사당 평균 항목 수를 카탈로그에 저장하고, 내부 조인은 테이블 크기와 이 통계로 nested-loop 비용을 추정해 탐욕적으로 순서를 정함(쓴 순서보다 2배 이상 싸 보일 때만 변경, `LEFT JOIN`·`ORDER BY … LIMIT`은 유지). 같은 점수의 인덱스는 통계로 선택. **⑤ ✅** covering index: 질의가 그 테이블에서 참조하는 컬럼이 모두 인덱스 키(collation 없는 컬럼)와 rowid뿐이면 인덱스 항목에서 행을 만들어 테이블을 읽지 않음(`EXPLAIN`: `USING COVERING INDEX`, 5만 행 범위 집계 139 → 11 ms). 잘린 긴 키는 테이블에서 읽음.
- 집합 연산(UNION 등)과 해시 조인의 빌드 측은 메모리에서 처리 (외부 정렬 미적용). `DISTINCT`·집합 연산의 중복 판정은 컬럼 collation이 아닌 이진 비교.
- 뷰는 조회 때마다 실행해 임시 결과로 사용 (조건 push-down 없음), 읽기 전용.
- FK: 부모 테이블이 먼저 있어야 생성 가능, 지연(DEFERRABLE) 제약·`SET DEFAULT` 미지원, `ALTER TABLE ADD COLUMN … REFERENCES/CHECK` 미지원. FK 컬럼에 인덱스가 없으면 부모 삭제 시 자식 테이블 전체 스캔.
- `VACUUM`은 실행 중 쓰기를 막고, 열린 스트리밍 커서가 닫힐 때까지 교체를 기다림. 복제본은 전체 스냅샷으로 재동기화.
- INSERT/UPDATE/DELETE는 플랜 캐시 대상 아님. 쓰기 시 페이지 인코딩은 여전히 변경마다 수행 (지연 인코딩은 4단계 인메모리 최적화와 함께 검토).

### 새 테스트가 찾아내 고친 결함
1. **체크포인트/복구 중단 시 DB 손상** (`kill -9` 토처 테스트가 4회차에 발견): 체크포인트와 복구가 헤더(0번 페이지)를 다른 페이지보다 먼저 써서, 그 사이에 죽으면 파일이 실제보다 새로운 커밋을 가리키고 복구가 필요한 WAL 커밋을 건너뛰었습니다. 헤더를 마지막에 쓰도록 수정했고, failpoint 재현 테스트를 추가했습니다. 수정 후 1,000회 모두 통과(응답한 커밋 손실 0, 진행 중 커밋은 전부 반영 353회·미반영 647회, 무결성 문제 0).
2. **B+트리 페이지 디코더 패닉** (퍼저 발견): 손상된 페이지에서 범위 밖 접근. 모든 필드 경계 검사 추가.
3. **행 디코더 메모리 폭주** (퍼저 발견): 손상된 값 개수만큼 미리 할당. 입력 길이로 상한 검사.

### 1단계에서 남긴 것 (2단계로 이동)
- **P1-14 (신규) 외부 정렬·대용량 그룹핑**: LIMIT 없는 `ORDER BY`, `GROUP BY`, `DISTINCT`는 여전히 메모리에서 처리.
- 드라이버 `ColumnTypes`, 이름 있는 파라미터 (P1-13 나머지).
- 열린 스냅샷이 오래 유지되면 WAL과 메모리 내 페이지 버전(최대 64 MiB, 초과분은 WAL에서 다시 읽음)이 커지는 구조적 특성 → 관측 지표(P2-1)로 노출 예정.

## 1. 결론 요약 (1단계 착수 전 평가)

현재 BangDB는 "**짧은 쿼리 위주의 단일 프로세스 임베디드 DB**"로는 쓸 수 있지만, 실서비스 DB로 쓰기 전에 반드시 고쳐야 할 문제가 있습니다.

| 영역 | 현재 수준 | 판단 |
|------|-----------|------|
| 데이터 안전성 (원자성·크래시 복구) | WAL·복구·문장 원자성 테스트 통과 | 양호. 단, 디렉터리 fsync 누락, 페이지 체크섬 없음 |
| 동시성 | 단일 writer + 리더 | **❌ 긴 읽기 쿼리가 모든 커밋을 막음 (실측 1분 50초)** |
| 자원 통제 | 쿼리 취소·타임아웃 없음, 결과 전체 메모리 적재 | **❌ 하나의 무거운 쿼리가 서비스 전체를 멈출 수 있음** |
| SQL 기능 | 기본 CRUD·JOIN·집계 | ⚠️ 서브쿼리, UPSERT, 복합 인덱스 등 앱 개발에 자주 쓰는 기능 부족 |
| 쿼리 성능 | 인덱스 동등/범위 검색은 양호 | ⚠️ OR, ORDER BY+LIMIT, 인덱스 없는 조인이 매우 느림 |
| 쓰기 처리량 | 트랜잭션 내 ~27µs/행 | ⚠️ 자동 커밋 ~1,300 커밋/초에서 포화 (그룹 커밋 없음) |
| 운영 | 온라인 백업·복제·CLI | ⚠️ 무결성 검사, 메트릭, 덤프/복원, VACUUM 없음 |

**권장:** 시계열·인메모리 확장보다 **1단계(운영 안정화, P0)를 먼저** 끝내야 합니다. 특히 P0-1(읽기가 커밋을 막는 문제)은 Pager 구조를 바꾸는 작업이라 이후 모든 확장의 기반이 됩니다.

### 순서에 대한 근거
- **P0-1을 가장 먼저**: Pager의 커밋/체크포인트 구조를 바꾸므로, 그 위에 올라갈 스트리밍 커서(P0-3), 그룹 커밋(P1-6), 체크섬(P0-5), 시계열 chunk가 모두 영향을 받습니다. 나중에 바꿀수록 비용이 커집니다.
- 복제는 Frame(페이지 이미지) 기반이므로 P0-1 이후에도 프로토콜 변경 없이 유지됩니다. 단, Frame 생성 시점이 "WAL append"로 바뀌는 것만 조정하면 됩니다.
- 복합 인덱스(P1-1)는 시계열(5단계)의 선행 조건이므로 2단계에 둡니다.

## 5. 사용 가이드 (6단계 완료 시점)

- **적합:** 앱에 내장하는 업무 데이터 저장(수 GB 이하, OLTP 중심), 여러 서비스가 공유하면 서버 모드, 읽기 확장은 복제본. 일반적인 웹 앱 스키마(복합 키, FK, UPSERT, 서브쿼리, 뷰, 윈도우·JSON 함수)를 그대로 쓸 수 있습니다. 측정·이벤트 데이터는 `USING timeseries`, 캐시성 데이터는 `USING memory`.
- **조회에는 타임아웃을:** `QueryContext`나 `Options.QueryTimeout`으로 상한을 두세요. 데이터가 크게 바뀐 뒤에는 `ANALYZE`를 실행하고, 느린 질의는 `EXPLAIN ANALYZE`와 `Options.OnSlowQuery`로 찾으세요.
- **FK 컬럼에는 인덱스를:** 부모 행 삭제·키 변경 시 자식 조회에 쓰입니다.
- **`Rows`는 끝까지 읽거나 `Close`:** 열린 커서는 스냅샷을 붙잡아 체크포인트와 `VACUUM` 교체를 미룹니다.
- **메모리 상한:** 큰 정렬·그룹핑은 `Options.SortMemory`를 넘으면 `Options.TempDir`의 임시 파일을 씁니다. 캐시는 `Options.CacheSize`.
- **대량 삭제 후:** 빈 페이지는 자동으로 재사용됩니다. 파일 크기를 줄이려면 한가한 시간에 `VACUUM`을 실행하세요 (실행 중 쓰기는 대기, 복제본은 재동기화).
- **대량 쓰기는 트랜잭션으로 묶기:** 동시 자동 커밋은 그룹 커밋으로 수천~1만 건/초, 트랜잭션 내 삽입은 행당 ~18 µs입니다.
- **정기 점검·백업:** `db.Backup()`을 주기적으로(특정 시점 복구가 필요하면 `replication.StartArchiver`), `db.IntegrityCheck()`(FK 검증 포함)를 배포 전·장애 후에 실행하고, `db.Stats()`를 모니터링에 연결하세요.
- **보안:** 디스크 암호화가 필요하면 `Options.EncryptionKey`(키는 DB 밖에), 네트워크는 서버 모드·복제 모두 TLS를 쓰세요.
- **장애 조치:** 복제본 승격(`Promote`)은 수동입니다. 승격 후 옛 primary는 새 term의 노드가 닿으면 스스로 읽기 전용이 되지만, 프로세스 중지·주소 전환을 함께 하세요.
