# 검토: BangDB 기반으로 시계열 DB와 인메모리 DB를 함께 개발하는 것이 적합한가?

## 결론 요약

**적합합니다. 단, "별도의 DB 3개"가 아니라 "하나의 코어 + 저장 엔진(테이블 유형) 3개" 구조로 가야 합니다.**

| 항목 | 판단 | 근거 |
|------|------|------|
| 인메모리 DB | **매우 적합** — 기본 형태는 이미 동작 중 (`:memory:`) | 저장소가 Pager 계층에서 분리되어 있어 SQL·트랜잭션·인덱스를 그대로 재사용 |
| 시계열 DB | **조건부 적합** — SQL·WAL·카탈로그는 재사용, 저장 구조는 새로 필요 | 현재 행 지향 B+트리는 시계열의 대량 append, 시간 범위 스캔, 압축, 보존 정책에 최적이 아님 |
| 진행 방식 | 공통 코어를 먼저 단단하게 → 저장 엔진 인터페이스 추출 → 인메모리 최적화 → 시계열 테이블 유형 | 코어의 결함은 세 제품 모두에 전파되므로 순서가 중요 |

## 1. 재사용할 수 있는 것과 없는 것

| 구성 요소 | 관계형 | 인메모리 | 시계열 |
|-----------|:------:|:--------:|:------:|
| SQL 파서 / AST / 식 컴파일러 | ✅ | ✅ | ✅ (함수 추가: `time_bucket`, `first`, `last`, `rate` 등) |
| 집계·그룹핑·정렬 실행기 | ✅ | ✅ | ✅ (시간 버킷 집계 최적화 추가) |
| 카탈로그 / DDL | ✅ | ✅ | ✅ (테이블 옵션 추가: 시간 컬럼, chunk 간격, 보존 기간) |
| 트랜잭션·락·세이브포인트 | ✅ | ✅ | ⚠️ 단일 writer로는 고속 수집에 한계 → 배치/그룹 커밋 필요 |
| Pager / WAL / 페이지 캐시 | ✅ | ✅ (메모리 저장소) | ✅ (chunk 파일들이 공유) |
| B+트리 (행 저장) | ✅ | ⚠️ 페이지 인코딩 오버헤드 | ⚠️ 최근 chunk의 쓰기 버퍼로는 사용 가능, 장기 저장은 부적합 |
| 행 인코딩 | ✅ | ✅ | ❌ 열 지향 + 압축 인코딩 필요 |
| `database/sql` 드라이버, CLI | ✅ | ✅ | ✅ |

전체 코드(테스트 제외 약 7천 줄) 중 SQL·실행기·드라이버·CLI 등 상위 계층이 약 75%를 차지하며, 이 부분은 세 제품이 그대로 공유할 수 있습니다. **이것이 같은 기반 위에서 개발할 가장 큰 이유입니다.**

## 2. 인메모리 DB

### 현재 상태
`bangdb.Open(":memory:")`는 이미 완전한 인메모리 관계형 DB입니다. Pager가 파일 대신 `map[페이지번호][]byte`를 쓰고 fsync가 없으므로, 트랜잭션·인덱스·조인 등 모든 기능이 동일하게 동작합니다.

### 한계
- 모든 접근이 "4KB 페이지 → 노드 디코드 → 수정 → 인코드"를 거칩니다. 디스크에서는 합리적인 비용이지만 메모리에서는 순수 오버헤드입니다 (프로파일 상 삽입 시간의 상당 부분이 `btree.decode/encode`).
- 영속성 옵션(스냅샷, AOF)이 없습니다 — 프로세스 종료 시 데이터가 사라집니다.
- TTL, pub/sub 같은 캐시형 기능이 없습니다.

### 권장 로드맵
1. **디코드된 노드 캐시** (단기, 효과 큼): Pager 위에 `pgno → *node` 캐시를 두고 커밋 시에만 인코드. 파일 모드 성능도 같이 좋아집니다.
2. **영속성 옵션**: 인메모리 데이터의 주기적 스냅샷(현재 파일 포맷 그대로 덤프 가능) + 커밋 로그(현재 WAL 형식 재사용).
3. **전용 인메모리 저장 엔진** (필요할 때만): 페이지가 아닌 Go 자료구조(예: 정렬된 B-tree of structs, skip list, 해시 인덱스)를 쓰는 `MemStore`. SQL 계층은 그대로 둡니다. Redis 같은 KV/TTL 용도가 확정될 때 진행해도 늦지 않습니다.

## 3. 시계열 DB

### 시계열 워크로드의 특성 vs 현재 구조

| 특성 | 필요한 것 | 현재 BangDB |
|------|-----------|-------------|
| 초당 수만~수백만 포인트 append | 메모리 버퍼 + 배치 플러시, 그룹 커밋 | 문장마다 B+트리 갱신, 단일 writer |
| 쿼리는 대부분 "시리즈 X의 시간 구간" | `(series, time)` 정렬 저장, 시간 범위로 chunk pruning | 단일 컬럼 인덱스만, 복합 키 없음 |
| 데이터 크기가 큼, 값 변화가 작음 | 열 지향 + delta-of-delta / Gorilla XOR 압축 (10배 이상 절감) | 행 단위 비압축 |
| 오래된 데이터 삭제 (보존 정책) | chunk 단위 drop (O(1)) | 행 삭제 시 재균형 없음 → 공간 회수 비효율 |
| 다운샘플링 / 연속 집계 | 시간 버킷 집계, materialized rollup | GROUP BY는 있으나 시간 버킷 함수 없음 |

### 권장 설계: 시계열을 "테이블 유형"으로 추가

```sql
CREATE TABLE cpu (
  ts    TIMESTAMP NOT NULL,
  host  TEXT,
  usage REAL
) WITH (timeseries, time_column = ts, chunk_interval = '1 day', retention = '30 days');

SELECT time_bucket('5 minutes', ts) AS t, host, AVG(usage)
FROM cpu
WHERE ts >= NOW() - INTERVAL '1 hour' AND host = 'web-1'
GROUP BY t, host ORDER BY t;
```

```
cpu (논리 테이블)
 ├─ chunk 2026-10-25  [활성]  B+트리 (key = series_id|ts) ← 기존 B+트리 재사용, 쓰기 버퍼 역할
 ├─ chunk 2026-10-24  [봉인]  열 지향 압축 블록 (ts: delta-of-delta, 값: Gorilla XOR)
 ├─ chunk 2026-10-23  [봉인]  ...
 └─ 보존 기간 초과 chunk → btree.Drop/free list로 통째로 회수 (이미 구현된 기능)
```

- 각 chunk는 카탈로그에 `(시작, 끝, 루트 페이지, 상태)`로 기록 → 플래너가 WHERE의 시간 범위로 chunk를 걸러냅니다 (현재의 접근 경로 선택 구조에 자연스럽게 들어맞음).
- 같은 파일/같은 WAL을 쓰므로 관계형 테이블(예: 장비 메타데이터)과 시계열 테이블을 **한 쿼리에서 JOIN** 할 수 있습니다. 별도 DB로 만들면 잃는 장점입니다.

### 선행 작업 (시계열 착수 전 코어에 필요한 것)
1. **저장 엔진 인터페이스 추출**: 현재 실행기가 `btree`를 직접 호출하는 부분(`exec.go`의 행/인덱스 유지, `plan.go`의 `scan`)을 `TableStore` 인터페이스(`Scan(range)`, `Get`, `Insert`, `Delete`, `EstimateRows`)로 분리.
2. **복합(다중 컬럼) 인덱스 / 복합 PK**: `(series, ts)` 키에 필수. 키 인코딩은 이미 prefix-free라 연결만 하면 됩니다.
3. **스트리밍 결과 커서**: 현재 결과를 전부 메모리에 적재하므로 대용량 시간 범위 조회에 부적합.
4. **배치 삽입 API + 그룹 커밋**: 다수 writer의 커밋을 한 번의 fsync로 묶기.

## 4. 리스크

| 리스크 | 영향 | 대응 |
|--------|------|------|
| 범위 확장(scope creep) | 세 제품 모두 미완성 | 아래 단계별 완료 기준을 지키고, 각 단계 종료 시 사용 가능한 상태 유지 |
| 코어 결함이 모든 제품에 전파 | 데이터 손상 | 코어 테스트 강화 (현재: 크래시 복구, 무작위 인덱스 vs 풀스캔 비교, 레이스 테스트). 퍼징 추가 권장 |
| 단일 writer 락 | 시계열 수집 처리량 한계 | 쓰기 버퍼 + 배치 커밋; 필요 시 chunk 단위 락으로 세분화 |
| 파일 포맷 변경 | 기존 DB 파일 호환성 | 헤더에 포맷 버전이 있으므로 지금부터 마이그레이션 규칙을 정해 둘 것 |

## 5. 추천 단계

| 단계 | 내용 | 완료 기준 |
|------|------|-----------|
| 0 (완료) | 관계형 코어: Pager/WAL, B+트리, SQL, 인덱스 플래너, 트랜잭션, 드라이버, CLI, `:memory:` | `go test -race ./...` 통과 |
| 1 | 코어 보강: 복합 인덱스, 스트리밍 커서, 노드 캐시, B+트리 병합/VACUUM, 서브쿼리 | 벤치마크 회귀 없음, 실제 프로젝트 1개에 적용 |
| 2 | `TableStore` 인터페이스 추출 (기존 B+트리 = `RowStore`) | 기존 테스트 무수정 통과 |
| 3 | 인메모리 최적화: 노드 직접 보관 저장소 + 스냅샷/로그 영속성 | 인메모리 삽입·조회 2배 이상 개선 |
| 4 | 시계열 테이블 유형: chunk, `time_bucket`, 보존 정책 → 이후 열 지향 압축 | 1천만 포인트 수집·구간 집계 벤치마크 |

**정리하면**, 관계형 DB를 공통 코어로 삼아 인메모리와 시계열을 "같은 엔진의 다른 저장 방식"으로 개발하는 것은 코드 재사용, 교차 조회(JOIN), 운영 단순성 면에서 적합합니다. 다만 시계열은 저장 구조가 근본적으로 달라야 하므로, 현재 B+트리를 그대로 쓰려 하지 말고 2단계(저장 엔진 인터페이스)를 먼저 끝낸 뒤 착수하는 것을 권장합니다.
